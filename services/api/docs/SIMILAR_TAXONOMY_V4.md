# Версионированная таксономия и отдельная выдача похожих кандидатов (v4)

**Важно:** строгая выдача `POST /employer/needs/{need_id}/recommendations` остаётся v3. Новая политика вызывается **явно**: `POST /employer/needs/{need_id}/recommendations/similar` с телом `{}` либо `{"minExperienceYears":3,"hardSkillIds":["python"]}`. Оба ответа — неизменяемые подборки, читаются через те же `GET /{snapshot_id}` и `GET /{snapshot_id}/items`. В кабинете работодателя отдельная кнопка «Найти похожих (v4)». Это политика поиска/ранжирования команды, не новая категоризация кандидата и не правило, указанное организатором ФСП.

## Источник и граница доверия

`app/modules/recommendations/config/` содержит локальную копию проекта `ranking/config` (версии `talent-taxonomy-v2`, `formal-filter-v2`): `roles.v1.json`, `grades.v1.json`, `skills.v1.json`, `filtering-policy.v1.json`, `sources.v1.json`. Валидатор проверяет версию, источники, уникальные ID/alias, направления связей, все края и узлы графа, полноту матрицы грейдов, коэффициенты и интервалы. Неисправная конфигурация блокирует создание новой подборки (503); старые snapshot читаются без неё. Источники/статусы соответствия внешним классификаторам содержатся в `sources.v1.json` и описаниях узлов; они **не** подтверждают навыки конкретного кандидата.

- **Нельзя** повышать грейд или присваивать роль по резюме, стажу, файлу ФСП или alias. Роль и грейд кандидата берутся только из успешной, завершённой v3-попытки (`qualification`). Тестируются `backend/frontend/fullstack × junior/middle/senior` (9 ячеек). `ml_engineer` и `data_engineer` есть только в диагностическом треке и не дают допуск без подтверждающего v3-теста. `professional_role`/профильный `stack` — самозаявленные и игнорируются для вычисления v4.
- Технические навыки кандидата для retrieval — только `subscores ≥ 50` из попытки, установившей категорию. `teamwork` не участвует. Алиасы (`postgres`→`postgresql`) равны 1, связанные понятия получают коэффициент только по явному ребру. Направленная матрица грейдов: Junior→Middle 0.80, Middle→Junior 0.98. На запрос Backend подтверждённый Frontend достижим через Fullstack за два ребра (`0.9×0.9=0.81`). Некоторые прочие роли также достижимы за два ребра; это **не** означает их подтверждённость у нынешних пользователей.

## Четыре стадии и неизменяемый порядок

1. **Hard gates:** роль работодателя и владение потребностью; email/публикация/приватность; подтверждённая `qualification`. Неизвестные/отсутствующие роли/грейды и явно перечисленные `hardSkillIds` исключаются. `hardSkillIds` должны входить в required/optional skills потребности. Диагностическая попытка, отсутствие теста, отозванное согласие — исключение до любых бонусов.
2. **Soft retrieval:** `filterFit` = произведение `role × grade × experience × stack × achievements × salary × work_format × location`, с порогом `0.12`. В текущем endpoint работодатель задаёт роль/грейд/skills через существующий `HiringNeed`, дополнительно может указать минимум лет опыта. Конфиг содержит также зарплату, формат, локацию и требования достижений, но у профиля и формы `HiringNeed` пока **нет сопоставимых структурированных полей** — для API они нейтральны (`1`), их не следует объявлять реализованными факторами UI. Запрос achievement tags API не принимает: достижения ФСП уже учтены в бонусе. Опыт не доказывает грейд.
3. **Качество:** существующие веса `qualityScore = .50×skillFit + .35×assessmentStrength + .15×fspBonus`. `skillFit` по результатам теста; бонус ФСП — лучший рекорд в явно синтетическом файловом реестре при связанном ID, отсутствие истории=0. **Без двойного счёта:** `Cstack` влияет лишь на включение в cohort, не умножает итог; `Cachievements=1` (нет требований), ФСП только в `fspBonus`. Для порядка `rankingFit = Crole×Cgrade×Cexperience×Csalary×Cwork_format×Clocation`, `finalScore = rankingFit×qualityScore`. Таким образом смежный кандидат входит в набор и имеет видимое понижение по роли/грейду, но один и тот же тестовый стек не штрафуется дважды.
4. **Snapshot:** сохраняются `v4-similar-taxonomy-v1`, версии taxonomy/filter для каждого элемента, восемь факторов и причин, `filterFit`, `rankingFit`, `qualityScore`, веса/компоненты, итог и весь упорядоченный cohort. Сортировка: finalScore DESC → qualityScore DESC → filterFit DESC → assessmentStrength DESC → candidateId ASC. `hasFspAchievements` для v4 выводится из сохранённого `fspBonus>0`, а не перечитывает изменившийся файл. Privacy перепроверяется на чтении; фильтры не пересчитывают места. Старые snapshot v3 не переписываются.

**Ограничение качества:** смежные роли/грейды — новая политика discovery, не подмена старого strict eligibility. Бонус синтетического файла не равен официальной верификации ФСП; будущая интеграция потребует доказательства владения FSP ID. Локальные коэффициенты — проверяемые гипотезы, не откалиброванная оценка качества найма на реальной популяции.

## Проверки

```sh
docker compose -f infra/docker-compose.yml run --rm --no-deps api pytest tests/test_taxonomy_filter.py tests/integration/test_similar_ranking.py tests/integration/test_similar_cohort.py -q
docker compose -f infra/docker-compose.yml run --rm --no-deps api pytest -q
docker compose -f infra/docker-compose.yml exec -T web npm run typecheck
```

`test_similar_cohort.py` строит **40** изолированных test-only кандидатов: две реально пройденные в тестовой среде подтверждающие формы (Backend/Frontend), остальные — синтетические копии проверяемых результатов с отдельными владельцами/попытками, различным стажем, самозаявленными ролями и стеком, приватностью, email/квалификацией и тремя FSP ID. Проверяются две политики (**17** кандидатов в строгой подборке против **34** в похожей из 40), смежная роль/грейд, ФСП, порядок, фильтр и неизменность snapshot. Это тест интеграции и инвариантов, **не** Precision@K на размеченных реальных наймах.
