# ФСП · IT-подбор — документация для Жюри (The Sopranos)

> Сжатая справка о продукте, сильных сторонах и юзкейсах. Состояние сверено с работающим
> сервисом (`http://localhost:3000`, API `:8000`) и логикой в репозитории. Пометки `[работает]` /
> `[нет]` — по фактическому прогону, а не по плану.

---

## 1. Что это

Не витрина вакансий и не парсер сторонних площадок, а **самостоятельный сервис, где работодатель
первым находит кандидата по подтверждённой категории, видит объяснение подбора и направляет
персональное предложение с обязательной зарплатой.** Кандидат заранее видит компанию, суть
предложения и диапазон, и сам решает, открывать ли контакт.

Обратная механика отличает продукт от классических job-борд: там работодатель тонет в
нерелевантных откликах, здесь он получает короткую объяснимую подборку по подтверждённой категории.

## 2. Сильные стороны

**Гибкость подбора, а не жёсткий отсев.** Формальная фильтрация мультипликативная и
«мягкая»: соседние роли/грейды/смежный стек не выкидываются, а получают коэффициент
(например, кандидат `fullstack` на вакансию `backend` — 0.9, `junior` на `middle` — 0.8).
Жёсткие gate — только приватность/верификация (verified email, согласие, попытка теста).

**Приоритезация навыков.** У потребности навыки делятся на `required` и `optional`
(optional с понижающим весом), плюс `hard_skill_ids` — безусловные «must-have». Покрытие
required весит больше optional, а hard-навык отсутствует → кандидат исключается.

**Проверка достоверности каждого навыка.** Грейд подтверждается тестом не «в сумме», а
понавыково: каждый вопрос несёт 1–3 `skillTags`, из них считается per-skill evidence
(`correct tagged / all tagged`). Для PASS нужны 13/18 technical **и** ≥50% evidence по каждому
core-навыку, для HIGH — 16/18 **и** ≥70%. «Дыра» в одном навыке не маскируется сильным соседним.

**Учёт достижений ФСП — ограниченный boost.** Ранжирование `0.50·skillFit + 0.35·testStrength
+ 0.15·fspBonus`. ФСП-бонус ограничен 0..1 и **не преодолевает eligibility-gate**: кандидат без
подтверждённой категории не попадает в выдачу, а история ФСП только усиливает позицию внутри
допущенной группы. Кандидат **без истории ФСП** работает корректно (`fspBonus=0`, не исключение).

**Приватность-first.** Контакты кандидата маскируются; они открываются только после принятия
приглашения (или собственного отклика). Зарплата `от–до` в рублях обязательна и в вакансии, и в
приглашении — кандидат видит условия до начала общения.

**Устойчивость и разделяемость теста.** 3 изоморфные формы A/B/C на ячейку, детерминированное
перемешивание вариантов (позиция ответа не выдаёт ключ), answer-key не отдаётся кандидату.
Дискриминация по грейдам проверяется синтетическими персонами (junior/middle/senior + gap).

## 3. Основные юзкейсы

### Кандидат
1. **Регистрация** — email + пароль, роль `candidate`. `[работает: 201]`
2. **Верификация email** — письмо с токеном (Mailpit), `POST /auth/verify-email`. `[работает]`
3. **Заполнение профиля** — ФИО, стек, специализация, самооценка грейда, согласия
   (обработка/публикация), приватность. `[работает: PATCH /me/candidate-profile]`
4. **Подтверждение грейда и навыков** — выбор специализации+грейда → тест (20 вопросов:
   18 technical + 2 teamwork) → subscore по каждому навыку → категория `специализация × грейд`.
   `[работает: 13/18 + per-skill gate → verifiedGrade + verifiedSkills]`

### Работодатель
5. **Регистрация + компания** — роль `employer`, затем `PUT /employer/company` (название,
   описание, контакты). `[работает]`
6. **Создание вакансии/потребности** — команда, специализация, min/target грейд, required/optional
   навыки. `[работает: POST /employer/needs]`
7. **Поиск кандидата** — фильтрация (специализация, грейд, категория, стек, ФСП) + ранжирование
   с объяснимым скором. `[работает: непустая выдача с компонентами и причинами]`
8. **Приглашение с зарплатой** — описание, компания, канал связи, диапазон `от–до`; статусы
   `sent → viewed → accepted/declined`. Контакты — только после accept. `[работает]`

## 5. Что сделано для замыкания сквозного сценария

1. **Синхронизирован банк вопросов.** В работающий сервис перенесён исправленный пул из `Sopranos/`:
   раздельные банки `junior/middle/senior` (без junior-дублей в middle), добавлены `fullstack` и `senior`
   → 9 ячеек (`backend/frontend/fullstack` × `junior/middle/senior`), 20 вопросов на форму (18 technical
   + 2 teamwork), 9 наблюдений на каждый core-навык.
2. **Убрано разделение demo/real/test.** Удалены поля `status`/`provenance`/`approval` (схема каталога и
   blueprint'ов), `status` из результата теста, `content_status` и `status` из таблиц попыток/форм
   (миграция `0012`), `diagnosticStatus` из профиля, пометка `fsp` (теперь источник
   `fsp`) и лейбл «Demo FSP bonus» (теперь просто «FSP bonus»). Квалификация определяется **только
   баллом** (13/18 pass, 16/18 high + per-skill gates), а не флагом «одобрено». Весь контент равноценен —
   при переносе в прод записи БД заменяются, а код работает с ними одинаково.
3. **Расширена схема приложения** (`catalog/v3.py`) под `fullstack`/`senior`; сквозной путь замкнут и
   проверен с нуля: регистрация → верификация email → профиль/согласия → тест → подтверждённая
   категория → непустая выдача (score + компоненты + причины) → приглашение с зарплатой → accept →
   раскрытие контактов. Чистое разворачивание `demo-reset.sh --purge` и 668 тестов — зелёные.

## 6. Оставшиеся честные ограничения

1. **ФСП-достижения — демонстрационный реестр.** Источник `fsp` — это демо-реестр (fixture), а не
   боевой провайдер ФСП; при подстановке реального реестра интеграция меняется только в одном адаптере.
2. Синтетическая валидация (персоны-агенты, Precision на размеченных парах) доказывает правила на
   сконструированных случаях, **не качество реального найма**.
3. **Известный дубль, ещё не устранённый:** в приложении остаются два трека тестирования
   (v3-подтверждающий и taxonomy-диагностический, `schemaVersion 2/3`), два скоринга (`score_v3` и
   `score_form`) и два каталога (`modules/catalog/` и `modules/recommendations/config/`). Консолидация
   в одну систему (3 роли) — следующий шаг.

## 7. Как воспроизвести

```sh
# Логика подбора и валидация теста (репозиторий Sopranos):
python3 arch/build_assessment_v3.py && python3 arch/validate_v3_skill_agents.py   # PASS
cd ranking && python3 -m unittest discover -s tests -q                            # 10 OK

# Работающий сервис (этот репозиторий):
docker compose -f infra/docker-compose.yml up -d
curl http://localhost:8000/health/ready          # {"status":"ok","db":"ok"}
# Web :3000 · API :8000 · Swagger :8000/docs · Mailpit :8025
# Тесты приложения: docker compose -f infra/docker-compose.yml exec -T api python -m pytest -q
```

**Ключевые артефакты:** правила скоринга и подбора — `business-logic/ASSESSMENT_AND_MATCHING_CONTRACT.md`
(репозиторий Sopranos); банк вопросов — `business-logic/questions-v3.json` + генератор
`arch/build_assessment_v3.py` + валидация `arch/validate_v3_skill_agents.py`; формальная фильтрация —
`ranking/filtering.py` и `ranking/config/*.v1.json`. В этом репозитории — `services/api/app/data/catalog/`
(blueprints v3 + manifest), `services/api/app/modules/catalog/v3.py` (схема blueprint),
`services/api/app/modules/assessments/` (скоррер, квалификация) и `services/api/app/modules/recommendations/`
(ранжирование и выдача).
